# Source-Aware Lookup Recovery — 2026-05-06b

Second 2026-05-06 measurement, **after** the source-aware lookup fix
in PR 0.5. Run against the identical dictionary state used by
[`2026-05-06-fi-summary.md`](2026-05-06-fi-summary.md) /
[`2026-05-06-et-summary.md`](2026-05-06-et-summary.md) (same DB at
`/tmp/finnestdb-baseline.db`); the only difference is the parser code.

**Commit**: TBD (PR 0.5 head)

## What changed in code

- [`internal/store/dict.go`](../../internal/store/dict.go) `BatchLookupForms`: step 1 now fetches all candidates and ranks them via `pickBestFormCandidate`. Ranking, higher-to-lower priority:
  1. Case-match: lowercase surface prefers lowercase lemma.
  2. POS sanity: lowercase surface demotes PROPN.
  3. Source priority (higher wins).
  4. Deterministic tiebreak: source asc, lemma asc, POS asc.
- [`cmd/importekilexdetails`](../../cmd/importekilexdetails/main.go): inserts now tag rows with `source='ekilex'`, `source_priority=20`, and `ensureSchema` runs `EnsureMultiLemmaSchema` + `EnsureDictionarySourceColumns` on a fresh DB.

**Lemma accuracy fully recovered** to April baseline (and slightly
beats it on `custom`). **POS accuracy recovered most of the way**
(94.3% vs April's 97.1% — small 2.8pp residual gap). **Coverage stays
at 100%** — no Ekilex enrichment was given up.

The residual POS gap is on tokens like `naeris` (NOUN turnip vs. VERB
"laughed", 1Sg past of `naerma`) and `keelt` (NOUN keel "language" vs.
NOUN kee "string"/different lemma form). These are genuinely
context-dependent and aren't fixable by case/POS heuristics alone —
they'd need contextual disambiguation (e.g. POS tagging from a
trigram model or a real morphological analyzer like Vabamorf).
