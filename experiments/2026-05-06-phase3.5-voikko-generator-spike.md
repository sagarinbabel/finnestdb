# Phase 3.5 — Voikko generator spike

Status: in progress
Date started: 2026-05-06
Plan reference: [`docs/LEXICAL_PLAN.md`](../docs/LEXICAL_PLAN.md) Phase 3.5 context

## Goal

Confirm a working paradigm-generation entry point against ~50 Kotus lemmas
covering the major inflection classes, before Phase 4 commits to a 6M-row
seed artifact. Also lock the Voikko-tag → UD-features mapping (e.g.
`[Sn][Ny]` → `Case=Nom|Number=Sing`).

The plan flagged three candidate paths because the originally-assumed
`voikkospell --paradigm` flag does not exist:

1. **libvoikko's internal VFST runtime via cgo, in inverse mode.**
2. **Build upstream Giellalt `lang-fin` + HFST toolchain from source**, then
   run `hfst-lookup` in inverse mode against the generator FST.
3. **Drop Voikko-as-generator entirely**; reframe Phase 4 as
   Voikko-analysis + Kotus-paradigm-table generation in Go.

## Environment

- macOS 26.3.1, arm64 (Apple Silicon)
- Homebrew 5.1.8
- `libvoikko` 4.3.3 (Homebrew bottle, installed 2025-09-29)
- `hfstospell` 0.5.4 (Homebrew bottle, libvoikko dependency)

## Path 1 — cgo against libvoikko's internal VFST runtime, inverse mode

**Verdict: infeasible without forking libvoikko.**

### What I checked

1. **Exported symbols in `libvoikko.1.dylib`.**
   `nm -gU /opt/homebrew/Cellar/libvoikko/4.3.3/lib/libvoikko.1.dylib`
   returns 68 externally-visible symbols, all `voikko*` C-API entry points
   listed above. No transducer, FST, generator, or inverse-lookup symbol.

2. **Internal C++ symbols in the dylib.**
   `nm` (without `-gU`) shows internal C++ classes: `libvoikko::fst::Transducer`,
   `libvoikko::fst::WeightedTransducer`, `libvoikko::morphology::VfstAnalyzer`,
   `libvoikko::morphology::FinnishVfstAnalyzer`. All marked lowercase `t`
   (local symbols) — not linkable from cgo.

3. **Source structure** (cloned `voikko/corevoikko` HEAD).
   - `libvoikko/src/morphology/` contains only `Analyzer*` classes
     (`Analyzer`, `VfstAnalyzer`, `FinnishVfstAnalyzer`, `HfstAnalyzer`,
     `LttoolboxAnalyzer`, `NullAnalyzer`, `AnalyzerFactory`). No
     `Generator*` class anywhere.
   - `libvoikko/src/fst/` contains the VFST runtime: `Transducer`,
     `UnweightedTransducer`, `WeightedTransducer`, `Configuration`,
     `Transition`. The public API on the transducers is `prepare(input,
     inputLen)` followed by iterated `next(outputBuffer)` — i.e. analyzer
     shape only.
   - The only `Generator*` matches in the entire source tree are
     `SuggestionGenerator{InsertSpecial,CaseChange,SplitWord,DeleteTwo,...}`
     under `spellchecker/suggestion/` — these mutate misspellings to
     produce candidate corrections; unrelated to morphological generation.

4. **VFST traversal direction.**
   `Transition` (in `libvoikko/src/fst/Transition.hpp`) stores both
   `symIn` and `symOut` per transition, so the *storage* is bidirectional.
   But `UnweightedTransducer::nextPrefix` and `WeightedTransducer`'s
   equivalent only walk transitions matching
   `inputSymbolStack[inputDepth] == currentTransition->symIn` and emit
   `currentTransition->symOut`. Reverse traversal (match `symOut`, emit
   `symIn`) does not exist anywhere in the codebase.

5. **Git history.**
   `git log --all --oneline -- '**/Generator*' '**/voikkogen*'` in the
   upstream `corevoikko` repo returns nothing — no removed-in-the-past
   generator either.

### Why "use the internal runtime via cgo" doesn't work

The original plan candidate assumed libvoikko had an internal generator
that just wasn't surfaced through the public C API. That's incorrect: the
runtime is hardcoded analyzer-direction. Making it work would require
either:

- **Patch and rebuild upstream libvoikko** to add a reverse-direction
  variant (e.g. `nextInverse` that swaps `symIn`/`symOut` matching), then
  expose a new C entry point. This is a real upstream contribution, not a
  cgo binding job.
- **Re-implement the VFST runtime in Go**, reading the same `mor.vfst`
  binary (header + symbol table + 8-byte `Transition` records + flag
  diacritics), but walking it inverse-direction. ~300–500 LOC including
  flag-diacritic semantics. Doable, but at that point the dependency on
  libvoikko-as-runtime is gone — it's a Go reimplementation that happens
  to read libvoikko's file format.

Neither of those is what "drive `mor.vfst` via cgo against libvoikko's
internal VFST runtime in inverse mode" actually means. So path 1 as
defined is infeasible. The variants that *are* feasible (fork+rebuild;
Go reimplementation) are larger commitments than path 2 and worth
ranking against path 3 on their own merits.

## Path 2 — Giellalt + HFST source build

**Verdict: works.** Generator FST builds cleanly on macOS arm64 once the
toolchain is assembled, and produces correct paradigm forms via
`hfst-lookup`.

### Toolchain assembled (machine-local, all under `/tmp` for the spike)

| Component | Source | Notes |
|---|---|---|
| HFST 3.17.1 | `apertium.projectjj.com/osx/nightly/arm64/hfst-latest.arm64.tar.bz2` | Prebuilt Apple Silicon nightly. Avoids the OpenFST/foma/SFST source-build dependency tree. |
| VislCG3 1.6.6 | `apertium.projectjj.com/osx/nightly/arm64/cg3-latest.arm64.tar.bz2` | Prebuilt. |
| zlib 1.3.2 | `brew install zlib` then symlink into `hfst/lib/libz.1.dylib` | Apple Silicon Homebrew omits libz; the prebuilt foma dep needs it. SIP strips `DYLD_LIBRARY_PATH` from subprocesses, so a symlink is the reliable fix. |
| ICU 77 (uconv) | `brew install icu4c@77` (already present), put `/opt/homebrew/opt/icu4c@77/bin` on PATH | Required for `generate-nfc-nfd-regex.bash` — see fix below. |
| autoconf, automake, libtool, gawk, GNU make | `brew install …` | Apple's `make` 3.81 is too old; gawk needed for `gensub`. |
| `giella-core`, `shared-mul`, `shared-smi`, `lang-fin` | `git clone github.com/giellalt/{...}` | All need to be sibling directories. |

### Build steps that just worked

```sh
# In each of giella-core, shared-mul, shared-smi:
./autogen.sh && ./configure --disable-configure-errors && make
# (—configure-errors flag waives optional Python test tools like gtgramtool)

# In lang-fin:
./autogen.sh
./configure --disable-configure-errors
make   # ~5–10 min; peak ~8.5 GB RAM during hfst-lexc
```

Output: `src/fst/{generator,analyser}-gt-{norm,desc,raw-desc}.hfst`,
plus `.hfstol` optimised-lookup variants. Generator is 15 MB, 446k
states, 1M arcs.

### One real bug fixed mid-build

`giella-core` ships [`scripts/generate-nfc-nfd-regex.bash.in`](https://github.com/giellalt/giella-core/blob/main/scripts/generate-nfc-nfd-regex.bash.in)
with a `@UCONV@` substitution. Its `configure.ac` falls back to
`false` if `uconv` isn't on PATH (`AC_PATH_PROG([UCONV], [uconv], [false])`),
which silently produces a degenerate `spellrelax-nfc2nfd.regex` — every
character gets a `(->) {}` rule — that `hfst-regexp2fst` then rejects with
"expression #1 contains only whitespace or comments". On macOS `uconv`
ships in Homebrew's keg-only `icu4c@77`, so `/opt/homebrew/opt/icu4c@77/bin`
must be on PATH at giella-core *configure* time. Once that's set, the
script regenerates the regex correctly and the build progresses through
orthography → phonetics → tagsets → cg3 → docs.

### Tag mapping (Giellalt → UD/Kotus)

The Giellalt tagset is more elaborate than the bare `+Sg+Nom` shape the
plan implicitly assumed. Key differences:

- **Inessive case is `+Ine`, not `+Iness`.** Same shape for `+Ela`,
  `+Ill`, `+Ade`, `+Abl`, `+All`, `+Ess`, `+Tra`, `+Abe`, `+Com`, `+Ins`.
- **Verbs need full Voice+Mood+Tense+Number+Person:** e.g.
  `+V+Act+Ind+Prs+Sg1` for "I do". Voices: `Act`, `Pss`. Moods: `Ind`,
  `Cnd`, `Imprt`, `Pot`. Tenses: `Prs`, `Prt` (preterite/past).
- **Infinitives have form + case:** A-infinitive is
  `+V+Act+InfA+Sg+Lat`; MA-infinitive is `+V+Act+InfMA+…+Ine` etc.
- **Some lemmas require `+CmpNP/None`** between POS and inflection in
  the `gt-desc` generator. This is the compound-NP marker — `gt-norm`
  drops it for many entries but not all. The safe pattern is:
  - run `analyser-gt-desc.hfst` on the bare lemma to see the canonical
    full tag string the FST expects;
  - reuse that prefix for paradigm enumeration through `generator-gt-desc.hfst`.

### Implication for Phase 3.5 → Phase 4

This path produces a usable generator. If we go this route, Phase 4
needs to decide:

1. **Which FST variant to seed from.** `gt-desc` has highest coverage
   but includes compound markers in the analysis. `gt-norm` is the
   "normative" surface variant. For a 6M-row seed, `gt-desc` is the
   safer choice.
2. **How to enumerate paradigm slots per lemma.** Either drive from
   Kotus class → expected slot list (so we know which case/number/voice
   combinations to ask the generator for), or do the lazy thing: ask
   the generator the cross-product of all case/number tags and discard
   `+?` rejections. The first is cleaner; the second is faster to ship.
3. **Tag → UD-features mapping.** Giellalt's `+N+Sg+Ine` maps to
   `Case=Ine|Number=Sing` (UD has `Ine`, `Ela`, etc. as case values
   directly). Verb tags need a richer mapping:
   `+V+Act+Ind+Prs+Sg1` → `VerbForm=Fin|Mood=Ind|Tense=Pres|Number=Sing|Person=1|Voice=Act`.
   This mapping is mechanical but needs a table; it's the actual
   deliverable the plan's "tag → UD-features" line was asking for.
4. **Distribution.** The generator FST is GPLv3. If we ship it as part
   of a seed artifact, downstream consumers inherit GPLv3 — same
   constraint as the originally-planned Voikko path. Alternatively we
   build offline once, run the generator to produce the seed
   `.jsonl.gz` (which is plain data, not GPL-derived FST code), and
   ship only the data. This is what `cmd/importvoikko` was going to do
   anyway and is the cleaner story.

### What this path is not

- Not "Voikko's generator" — it's the **Giellalt** Finnish FST
  pipeline. Voikko's Finnish FST is a Voikko-format compilation of an
  older snapshot of the same Giellalt source, but with Voikko-specific
  filters. The plan's title "Voikko generator spike" should probably be
  renamed; the practical path is Giellalt-direct.
- Not free of yak-shaving on a fresh machine: there's a real
  20–30-minute install + first-build cycle, and the `uconv` configure
  bug above is a foot-gun. But it's a one-time cost — once the FST
  exists you can re-run paradigm generation cheaply.
